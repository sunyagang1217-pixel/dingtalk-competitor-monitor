# 分步对话流程

## 1. 先确认目标和环境

先判断是否存在会实质改变结果的问题。确认用户要监控的是“竞品公开动向日报”，首版运行于 Codex Desktop 与本地 macOS，并确认项目输出目录。一次最多问 1-3 个紧密相关的问题。

不要一开始索取 Webhook 或加签密钥。用户主动贴出凭据时，立即提醒轮换，并且不要把原值写入文件、命令或回复。

## 2. 定义监控口径

依次收集并复述：

1. 行业边界，以及希望关注的产品、价格、促销、渠道、合作、融资、团队、技术、政策或口碑等动向。
2. 国内和海外范围；竞品正式名称、英文名、旧名、产品名等别名；每个竞品的 1-5 优先级。
3. 时区、发送时间、星期、采集回看天数、日报条数、国内与海外优先配额。
4. 日报格式：分析版包含“发生了什么”和“值得关注”；快讯版只保留核验后的事实摘要。
5. 发现来源默认同时启用 Google News、百度搜索、360 搜索和微信公众号搜索，四类来源同级，不设主次；仅在用户明确要求或环境无法使用时停用某一类。

竞品名称有歧义时先确认，不要自行把同名公司或同类关键词当作别名。对用户只提供品牌名的情况，可提出别名建议，但必须让用户确认。

Google News、百度和 360 使用竞品查询式。微信公众号搜索始终使用全部竞品名称及别名，不附加行业词限制，以发现所有提及竞品的公众号文章，不限官方账号。国内和海外竞品对所有启用来源一视同仁。

## 3. 确认固定质量规则

向用户说明并确认以下默认规则：

- 搜索结果只用于发现线索，发送前必须打开原始报道、公众号文章、竞品官方页面或官方公开公告。
- 无法读取原文、时间超窗、标题与正文不一致或来源不可靠的条目删除。
- 同一期合并重复报道；跨期使用规范化标题指纹和 SQLite 已发送状态去重。
- 推断与事实分开；宣传稿中的企业口径使用“宣称”“发布”或“推广”等措辞。
- 法院公告、裁判文书和监管公告直接涉及竞品的合同、退款、处罚或合规事件时可以保留，但必须标注公告性质、涉事主体和真实日期。
- 已确认但需要延期的条目进入 `data/pending_articles.json`；到达 `send_after` 后必须重新打开原文核验，成功发送后才标记 `sent`。
- 至少一个启用来源成功且所有候选经核验后被排除，才允许空日报；全部来源失败时不发送、不记账。
- 默认不 `@` 任何人。

## 4. 展示派生摘要并停下确认

生成文件前，展示：项目名称与 slug、绝对输出路径、行业、地区、竞品和别名、优先级、查询式、时间、时区、星期、回看天数、条数配额、日报格式、四类启用来源、公众号检索口径、官方公告口径、延期策略、来源核验和去重规则。

等待用户明确回复“确认生成”或同等含义。用户只确认部分内容时，不视为整体确认。

## 5. 生成并离线验证项目

按照 `spec-schema.md` 写一个不含凭据的 JSON 规格到当前工作区的 `work/`，然后运行脚手架。安装依赖并运行：

```bash
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
PYTHONPATH=src .venv/bin/python -m competitor_monitor_bot.cli preview \
  --title "连接测试预览" \
  --text "这只是本地预览，不会发送。"
```

此阶段不得运行 `send` 或 `send-analysis`。

## 6. 在终端配置凭据

读取 `dingtalk-safety.md`。把项目的 `./scripts/configure_dingtalk.sh` 命令给用户，让用户在自己的终端中运行。明确说明粘贴后没有字符回显是正常现象，并让用户只回复“配置校验通过”或错误文本，不回复凭据。

这是一个必须等待用户完成的停点。不要在聊天中代收、回显、猜测或复用任何凭据。

## 7. 发送连接测试

配置校验后，先本地生成测试消息。向用户完整展示：

- 目标：当前 Webhook 绑定群；Webhook 本身不能可靠显示群名。
- 完整标题。
- 完整正文。
- `@` 行为，默认“不 @ 任何人”。

等待用户明确确认这条消息后，才运行一次受保护的 `send` 命令。成功响应只报告 `errcode`、`errmsg` 和已发送状态，不输出签名 URL。随后等待用户确认群内已收到。

## 8. 验证首份正式日报

运行 `collect-json` 后，先检查 `collection.enabled_sources`、`successful_sources` 和脱敏后的 `source_errors`。全部启用来源失败时停止；部分来源失败时保留失败记录并继续核验其他来源。

读取 `data/pending_articles.json`；已到 `send_after` 的 `review_status=verified` 条目必须合并并重新核验。逐条打开原始来源并按照项目中的 `config/analysis_prompt.md` 填写真实来源、真实发布时间、日期精度、内容属性和分析字段。运行 `analysis-preview`，把最终完整日报展示给用户。等待用户确认内容、目标群和 `@` 行为后再发送。

用户确认收到首份日报后，才进入定时任务设置。

## 9. 设置定时任务

读取 `automation-workflow.md`。先展示最终自动化摘要并取得明确授权。未授权自动发送时，只创建“生成草稿并提醒确认”的任务；不要创建会自动调用 `send-analysis` 的任务。
